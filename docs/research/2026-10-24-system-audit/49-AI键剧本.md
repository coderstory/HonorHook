## 2. 改写命令模板（content 路径，唯一可用写路径）

JSON 本身只含双引号不含单引号 → **外层用单引号包 value，内层 JSON 原样**，无需额外转义。
`intent:#Intent;...;end` URI 中的 `=` 存储形态是 `\u003d`（CCM 下发如此）——照抄原值风格，自己写新 URI 时**同样用 `\u003d`**（解析端按原样读）。

### 模板 A：改已有行（update，双击/长按/白名单都已有行，日常用这个）
```bash
su -c "content update --uri content://settings/system \
  --where \"name='ai_key_double_click_service_info'\" \
  --bind value:s:'<新JSON>'"
```

### 模板 B：插入新行（仅当 query 查不到该行时；name+value 双 bind）
```bash
su -c "content insert --uri content://settings/system \
  --bind name:s:'ai_key_double_click_service_info' \
  --bind value:s:'<新JSON>'"
```

### 通用读回验证
```bash
su -c 'content query --uri content://settings/system --where "name='\''<键名>'\''"'
```

## 3. 三个示范配置（完整可粘贴）

### a) 双击 → 手电筒（系统组件）
> ⚠️ 手电筒 Activity 组件名各版本不同，执行时先实测组件存在：
> `su -c 'pm dump com.hihonor.camera | grep -i flash'`（候选：`.controller.FlashlightActivity` / systemmanager 下 Flashlight）。
> 备选稳妥法：不改 Intent 而用 `action=android.intent.action.TORCH` 类系统 action 不可靠；**首选实测到的组件**。以下以 `com.hihonor.camera/.controller.FlashlightActivity` 为占位：

```bash
su -c "content update --uri content://settings/system --where \"name='ai_key_double_click_service_info'\" --bind value:s:'{\"commonIntent\":\"intent:#Intent;package\\u003dcom.hihonor.camera;component\\u003dcom.hihonor.camera/.controller.FlashlightActivity;S.pressMethod\\u003ddouble_press;end\",\"isSubService\":false,\"isSupportScreenLockStart\":\"0\",\"launchAnim\":\"1\",\"lockScreenIntent\":\"\",\"longPressUp\":\"0\",\"packageName\":\"com.hihonor.camera\",\"serviceId\":\"system_camera\",\"sourceType\":\"ccm\",\"startType\":0}'"
```

### b) 长按 → 任意三方 app（示例：Firefox）
> 先确认入口：`su -c 'cmd package resolve-activity --brief -c android.intent.category.LAUNCHER org.mozilla.firefox'`
> （换成任意已装 app；若目标包不在白名单需同步 §3b2 改 ai_key_whitelist_control）

```bash
su -c "content update --uri content://settings/system --where \"name='ai_key_long_service_info'\" --bind value:s:'{\"commonIntent\":\"intent:#Intent;package\\u003dorg.mozilla.firefox;component\\u003dorg.mozilla.firefox/.App;S.pressMethod\\u003dlong_press;end\",\"isSubService\":false,\"isSupportScreenLockStart\":\"0\",\"launchAnim\":\"1\",\"lockScreenIntent\":\"\",\"longPressUp\":\"0\",\"packageName\":\"org.mozilla.firefox\",\"serviceId\":\"custom_app_1\",\"sourceType\":\"ccm\",\"startType\":0}'"
```

**b2) 白名单加入三方包（type 0=包名 整包放行；type 1=组件 精确放行）**：
```bash
su -c "content update --uri content://settings/system --where \"name='ai_key_whitelist_control'\" --bind value:s:'{ \"version\": 2, \"foregroundIgnoreApps\": [], \"directDispatchApps\": [ \"com.hihonor.camera\" ], \"allowDispatchList\": [ { \"type\": \"0\", \"value\": \"com.hihonor.camera\" }, { \"type\": \"0\", \"value\": \"org.mozilla.firefox\" }, { \"type\": \"1\", \"value\": \"com.hihonor.tips/com.hihonor.tips.detail.ui.DetailActivity\" } ] }'"
```

### c) 锁屏拉起（isSupportScreenLockStart 保留写法）
关键三点：`isSupportScreenLockStart:"1"` + **lockScreenIntent 必须指向一个 isolated/secure 任务 affinity 或 selffinish 型 Activity**（原厂模式：锁屏用 SecureCameraActivity / SelfFinishActivity，即「锁屏专用壳页」）+ 保留 commonIntent 供解锁态使用。示例=保持双击相机原值即是完整范例（见 §1 存档）。三方 app 想锁屏拉起时设 `"isSupportScreenLockStart":"1"` 并给 `lockScreenIntent`（可指向 `android.intent.action.MAIN` 的 LAUNCHER activity，若系统 SELinux/锁屏策略拦截则表现为无反应，需回退）。

## 4. 验证与回滚

**验证**：
1. 读回：§2 通用读回命令，逐字节比对写入 JSON。
2. 实测：解锁态按 AI 键（双击/长按）→ `logcat | grep -iE "KeyAction|brain"` 看 `handleKeyAction(channel=..., pressMethod=...)`；无该日志=键事件没进 brain（改的是错误层）；有日志无启动=JSON 校验失败。
3. 锁屏态实测 lockScreenIntent。

**失败现象对照**：
- 按键无反应：① JSON 格式错（读回肉眼查引号/`\u003d`）② brain **缓存旧值未重读** → 试 `su -c 'am force-stop com.hihonor.brain'`（它由系统服务拉起会自动重启；若 force-stop 被系统保护拒绝，则重启手机一次）。③ 目标包被白名单拦截（logcat 有 dispatch deny 类日志）→ 改 whitelist_control。
- 拉起的是相机而非新目标：brain 内置 system_camera 直发通道（directDispatchApps）优先 → 把目标加白名单或换 serviceId。

**回滚**（value 换成 §1 存档原值，同样 content update）：
```bash
su -c "content update --uri content://settings/system --where \"name='ai_key_double_click_service_info'\" --bind value:s:'<§1存档JSON>'"
# long / whitelist_control / short 同理；support_press_method 未改则无需动
su -c 'am force-stop com.hihonor.brain'   # 逼重读
```

## 5. 风险与未定点

1. **brain 读取时机未实证**：settings 读取可能发生在按键时实时读（低风险）或开机/进程启动缓存（改后需 force-stop brain 或重启）。剧本默认改完就 force-stop brain 一次，成本最低。
2. **CCM 云控回写**：sourceType=ccm 表示值来自云端配置，云端可能随时下发覆盖本地改动（48 号风格风险）。观察到"改了又变回"即此原因——非剧本失败。
3. **白名单语义**：directDispatchApps（直发相机通道）与 allowDispatchList（type0 包 / type1 组件）两套并存；三方包是否必须入 allowDispatchList 才会被分发**未实证**，b) 示例已附带同步加白名单命令以保成功率。
4. **isSupportScreenLockStart 字符串型**（"1"/"0" 是字符串非数字），写错类型可能解析失败。
5. intent URI 里 `\u003d` 转义是 CCM 原始风格；若实测解析端接受裸 `=` 也可，但**回滚值必须原样含 `\u003d`**。
6. 手电筒组件名未实测（§3a 给了实测命令），执行卡第一步先做。
