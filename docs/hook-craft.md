# 怎么写好 hook（本项目实战方法论）

> 只写"**代码里读不到**"的判据与教训：选点原则、失败模式、本项目踩过的坑。
> API 写法 / 工程脚手架见 skill `lsposed-hook-expert`、`build-lsposed-module`；样本级详证见各 skill 的 `references/`。
> 逆向侧对应文档：[`reverse-craft.md`](reverse-craft.md)。哲学总纲：`hook-philosophy-manifesto.md`。

## 一、选点决定 90% 成败

| 原则 | 含义 | 本项目实证 |
|---|---|---|
| **找决策，不找表现** | 改做决策的地方（开关判定/数据构造），不改最终 UI 展示 | 改 `ItemInfo` 判定一处 → 列表/详情/搜索全生效；改 `setVisibility` 要逐页覆盖且逐版漂移 |
| **根源原则：改数据源，不挂消费端** | 数据源一处改、下游全生效；消费端散落多处且随版本增删 | 云控统一读点（`u15.getBoolean` 唯一出口）→ 表驱动；`getVipOnly` 优先于 `isVipResouce` |
| **出口裁剪**（服务端载荷类） | 在"服务端载荷 → 域模型"的**唯一出口**裁剪，不在各消费方逐个 GND | 槽位 `SlotData.getList()`、底 tab `BottomTabConfigs`；改完一处，所有页面都不再渲染 |
| **找收口点** | 一个稳定入口覆盖一整类行为，版本无关 | 原生弹窗全走 `Dialog.show()`；`WindowManagerGlobal.addView` 兜底悬浮窗 |
| **门 ≠ 仲裁者** | `isXxxShow` 类"门"只是入口判断；拦死门会让后续更新逻辑整段不执行 | `isBuyBtnShow` 返 false ⇒ `updateButtons` 不跑 ⇒ 按钮停在 XML 初始态（真机"hook 了但没变"的头号原因）。正解 = 放行门 + 改真正的仲裁输入（按钮类型/数据态） |
| **浅签名优先** | 每多一个具体类型依赖，版本破坏概率就多一分 | 无参返 boolean ≫ "第 2 参必须是某 DTO 且内部有 int 字段" |
| **最少点** | 每个点都是版本漂移暴露面 | 审计删点优先于加点；但删点必须真机 A/B（见 §四） |

## 二、四类"改了也没用"的死点（本项目全部踩过）

1. **服务端下发字段**：文案/内容由服务端生成 ⇒ 客户端伪造 getter 无效。实证：主题商店「VIP 已过期」真实来源是服务端 `secondTitle`，须单独判空隐藏。
2. **null 实例**：getter 短路对 `null` 无意义。实证：`getVipState()` 首查未落缓存时返 null，UI 直接走"已过期"分支 ⇒ 需在漏斗层自建实例填值。
3. **类内直读字段**：`equals/copy/writeToParcel/toString` 不经 getter ⇒ 只短路 getter 覆盖不到。
4. **休眠链**：静态存在 ≠ 运行时被调用。挂之前先数**消费点数**；零调用者 = 死挂载（挂了永不生效）。

## 三、旁路与缓存：同一配置往往有多条读链

改一处不够，要问"这条配置还有别的读取路径吗"：
- 实证（底 tab）：AMS 在线配置链之外还有 **MMKV 缓存链**直解配置；且宿主 fallback 分支（列表 null / size 越界）会**本地硬编码重建**入口 ⇒ 单清缓存反而必然复活。处置 = 在渲染前**就地裁剪**（PRE_PROCESS），脏缓存无所谓。
- 通用问法：这份数据经不经缓存？失败的 fallback 会不会自己造一份？StateFlow/广播有没有旁路更新？

## 四、挂载基建与解析（本项目形态）

- **表驱动 + 单一事实源**：功能 key 集中在 `FeatureCatalog`（双端共用，禁止任一侧手写 key 字符串）；加/改开关只动表。**默认全开**语义：读不到/异常/未写入一律视为开；关某功能 = 宿主显式写 false，且**下次目标进程注入才生效**。
- **双轨解析**：直连反射优先（不缓存——赌类稍后加载）→ DexKit 特征兜底。混淆目标必配**内容性锚点**（混淆不改字符串常量/参数类型序列）⇒ 无锚点就诚实跳过（`NOT_RESOLVED`），**不猜类名硬兜**。
- **失败分级**：`FAILED` = 挂载抛异常，重试无意义；`NOT_RESOLVED` = 类/依赖未就绪，随类加载重试。
- **挂载类型要分**：改返回值 / 条件短路（只对目标参数生效，避免误伤无关判定，如 `hasPrivilege(14)` 只短路特权位 14）/ 前置改写（PRE_PROCESS，proceed 前修状态、失败不动）/ 键值覆盖（KEY_OVERRIDE，表驱动云控）。
- **幂等与防重装**：挂在注册表层保证；实现内不加 installed 标志；多包共享进程需对象级去重。

## 五、防御与可观测（底线，不是加分项）

- **异常隔离**：hook 回调里任何异常都必须吞掉并记日志——绝不能炸宿主进程。
- **per-key 降级**：每个子功能可独立关，而不是逼用户卸载模块。
- **日志是黑盒里唯一的眼睛**：判据统一 `installed N/M` 汇总；触发类日志节流，别刷屏。注意**宿主 logger 的 INFO 常不落 logcat**（只有 WARN/ERROR）⇒ 载荷类证据要靠模块侧探针打。

## 六、验证铁律（本项目血泪）

1. **判据先对版本**：真机 UI 与结论不符时，第一步 `dumpsys package` 对宿主版本 vs 逆向基线；`installed N/M` 里 N 明显小于 M = 版本错位或选点失效，**别先改 hook 实现**。
2. **目标方法存在性以设备实机 APK 的 dex 为准**：`adb shell pm path` 拉包 → dex 字符串检索。jadx 产物只作阅读参考（曾出现 jadx 有 `getIsVipUser`、设备包只有 `isVipUser` ⇒ 真机挂载失败）。
3. **删点必须真机 A/B**：静态推理"这段冗余"被真机回归打脸过一次（漏斗/旁路/null 实例都出自静态推理的盲区）。
4. **重装即被停用**：覆盖安装后 LSPosed 停用模块（表现为进程活着但零模块日志）⇒ 重新启用；按需拉起的进程还需 force-stop 一次。
5. **破坏性效果不由 AI 实测**：AI 交付 = 代码 + 构建通过 + 用户自执行的验证清单。
