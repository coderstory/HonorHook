# 怎么写好 hook（本项目实战方法论）

> 只写"**代码里读不到**"的判据与教训：选点原则、失败模式、本项目踩过的坑。
> API 写法 / 工程脚手架见 skill `lsposed-hook-expert`、`build-lsposed-module`；样本级详证见各 skill 的 `references/`。
> 逆向侧对应文档：[`reverse-craft.md`](reverse-craft.md)。哲学总纲：`hook-philosophy-manifesto.md`。

## 一、选点决定 90% 成败

| 原则 | 含义 | 本项目实证 |
|---|---|---|
| **找决策，不找表现** | 改做决策的地方（开关判定/数据构造），不改最终 UI 展示 | 改 `ItemInfo` 判定一处 → 列表/详情/搜索全生效；改 `setVisibility` 要逐页覆盖且逐版漂移 |
| **根源原则：改数据源，不挂消费端** | 数据源一处改、下游全生效；消费端散落多处且随版本增删 | 云控统一读点（`u15.getBoolean` 唯一出口）→ 表驱动；`getVipOnly` 优先于 `isVipResouce` |
| **出口裁剪**（服务端载荷类） | 在"服务端载荷 → 域模型"的**唯一出口**裁剪，不在各消费方逐个 GND | 槽位 `SlotData.getList()`、底 tab `BottomTabConfigs`；改完一处，所有页面都不再渲染 |
| **找收口点** | 一个稳定入口覆盖一整类行为，版本无关 | 原生弹窗全走 `Dialog.show()`；`WindowManagerGlobal.addView` 兜底悬浮窗 |
| **门 ≠ 仲裁者** | `isXxxShow` 类"门"只是入口判断；拦死门会让后续更新逻辑整段不执行 | `isBuyBtnShow` 返 false ⇒ `updateButtons` 不跑 ⇒ 按钮停在 XML 初始态（真机"hook 了但没变"的头号原因）。正解 = 放行门 + 改真正的仲裁输入（按钮类型/数据态） |
| **浅签名优先** | 每多一个具体类型依赖，版本破坏概率就多一分 | 无参返 boolean ≫ "第 2 参必须是某 DTO 且内部有 int 字段" |
| **最少点** | 每个点都是版本漂移暴露面 | 审计删点优先于加点；但删点必须真机 A/B（见 §四） |

## 二、四类"改了也没用"的死点（本项目全部踩过）

1. **服务端下发字段**：文案/内容由服务端生成 ⇒ 客户端伪造 getter 无效。实证：主题商店「VIP 已过期」真实来源是服务端 `secondTitle`，须单独判空隐藏。
2. **null 实例**：getter 短路对 `null` 无意义。实证：`getVipState()` 首查未落缓存时返 null，UI 直接走"已过期"分支 ⇒ 需在漏斗层自建实例填值。
3. **类内直读字段**：`equals/copy/writeToParcel/toString` 不经 getter ⇒ 只短路 getter 覆盖不到。
4. **休眠链**：静态存在 ≠ 运行时被调用。挂之前先数**消费点数**；零调用者 = 死挂载（挂了永不生效）。

## 二·2、门归谁：先判定"客户端的门"还是"服务端的门"

伪造本地状态前先问一句：**这个决定权在客户端还是服务端？** 判错方向的代价不是"没效果"，而是**更糟**（见下）。

| 信号 | 归属 | 客户端能做的 |
|---|---|---|
| 本地计算的字段（boolean/int/串） | 客户端 | 完全决定结果 |
| 只被 UI **读取**的服务端字段 | 服务端 | 只改显示，改不了权限 |
| 服务端签发的下载/播放 URL | 服务端 | **做不到**——无法凭空造出合法 URL |
| 每次受保护操作都回服务端验的权益 | 服务端 | 做不到 |
| 服务端值的本地缓存 | 服务端（缓存） | 只骗 UI 到下次刷新 |

**最快验证法（几分钟，别猜）**：直接打那个接口——① 无凭据调受保护端点 ⇒ 401/403 = 服务端把关；② 伪造 token 再调 ⇒ 仍 401 = token 真被验；③ 调元数据端点 ⇒ 常 200 但**故意不含**资源 URL；④ 关键字段"根本不存在于响应里" ⇒ 任何客户端改动都造不出来。
> 本项目实证：exam8「阅后即焚」= 试卷页可进（客户端门过了）、正文取不到（服务端按订单态下发）——属第 ③④ 类。

## 二·3、伪造会员态的两种失败模式（本项目两个目标都属此类）

强制 `isVip()` 类方法返 true 是经典做法，但有代价：

1. **只改外观**：UI 显示会员样式，受保护动作仍在服务端失败。
2. **主动有害**：客户端"以为"自己持有并不存在的权益，于是走进**需要服务端数据**的代码路径 ⇒ 实测后果是**白屏**（进程活着、什么都不渲染，只有一个被吞掉的异常）。

因此：① **不要伪造会 gate 数据获取的权益**；② 若该标志同时用于权限判定，**优先改它的展示消费者，而不是它的计算**（改表现不授权限）。

## 三、旁路与缓存：同一配置往往有多条读链

改一处不够，要问"这条配置还有别的读取路径吗"：
- 实证（底 tab）：AMS 在线配置链之外还有 **MMKV 缓存链**直解配置；且宿主 fallback 分支（列表 null / size 越界）会**本地硬编码重建**入口 ⇒ 单清缓存反而必然复活。处置 = 在渲染前**就地裁剪**（PRE_PROCESS），脏缓存无所谓。
- 通用问法：这份数据经不经缓存？失败的 fallback 会不会自己造一份？StateFlow/广播有没有旁路更新？

## 四、挂载基建与解析（本项目形态）

- **表驱动 + 单一事实源**：功能 key 集中在 `FeatureCatalog`（双端共用，禁止任一侧手写 key 字符串）；加/改开关只动表。**默认开（2026-10-15 用户拍板）**语义：读不到/异常/未写入一律回 FeatureCatalog 目录默认（默认开；例外关 = hide_5g / hide_sim2 / 清后台 A/B 互斥对）；关某功能 = 宿主显式写 false，且**下次目标进程注入才生效**。
- **三阶段解析**：直连反射优先（不缓存——赌类稍后加载）→ DexKit **严格轨**（方法名/签名都钉死，只治类名漂移）→ DexKit **宽松轨**（只用内容锚点查，旧名字/签名降级为排序依据，治方法名与实现类整体漂移）。混淆目标必配**内容性锚点**（混淆不改字符串常量/参数类型序列）⇒ 无锚点就诚实跳过（`NOT_RESOLVED`），**不猜类名硬兜**；宽松轨只在候选唯一胜出时采纳，歧义/重复一律跳过并留日志。
- 兜底轨的诚实规则：严格轨命中**优先声明类精确匹配**，类名整体漂移时只接受"唯一候选"；候选集不完整（`getMethodInstance` 失败）或 DexKit 桥/查询瞬时失败 ⇒ 本轮**不做判定也不缓存 miss**（下轮类加载重试）——静默丢弃的候选可能正把"并列"翻转成"唯一"。宽松轨候选"全部不可挂载"要跳到下一层查询继续（那是"没有可用命中"，不是"并列歧义"）。
- 兜底轨**允许 static**：`DexHitSelector.isHookable` 只排除 abstract/native（旧实现误抄 Rain 的 `Modifier.isStatic` 过滤，导致静态实现整体收不到 DexKit 兜底）。签名串带 `static` 前缀——旧实例点被挂到 static 上时 `thisObject` 为 null，依赖 thisObject 的拦截器会静默空转，漂移日志是唯一现场。
- **DexKit 三阶段的七条修正**（2026-10-20 复审，installer 38.301 全线漂移逼出来；纯逻辑部分已钉进 JVM 单测）：
  ① **严格轨无内容锚点不猜**——唯一候选也不采纳（此时只剩「名字+签名」这种弱特征，同名方法全 APK 一大把，猜错会直接改坏宿主行为），交宽松轨；宽松轨也无锚点 ⇒ 诚实 `NOT_RESOLVED`。
  ② **宽松轨 L1 只用 `usingStrings`**（方法体串）；类锚点层（`classStrings`）另加**声明类硬约束**——类锚点多是类内 TAG，同串也会出现在别的类（UI 串/布局名尤其容易），不加约束会把候选铺满全 APK。
  ③ **`instanceOnly` 标记**：依赖 `thisObject` 的拦截器**不许挂 static**——挂上后 `thisObject` 恒 null，判据行照样打 `installed N/M`，功能却静默空转（判据能绿、功能不生效的典型）。
  ④ **两挂载点落到同一方法 = 合并，不是失败**：记「合并」并**合并计成功**（不扣 N、不进失败清单），但留一行 WARN 让判据可审计（谁与谁合并）。
  ⑤ **返回类型比较走 `canonicalTypeName` 归一**（`int` ≡ `java.lang.Integer`）——此前只参数侧归一，返回侧漏了 ⇒ 整批候选被丢弃。
  ⑥ **严格轨弃权要留 WARN**（有候选却未采纳）——否则 miss 缓存把它钉死，日志上看不出原因。
  ⑦ **漂移 WARN 按 `task.id` 节流**——漂移是每 task 一次的定性事实，重试轮各打一行只会刷屏。
- **宿主版本读取纪律**：`ActivityThread.currentPackageManager` 在现代 AOSP **根本不存在**（Android 14 源码全文 0 命中，真机 `getMethod`/`getDeclaredMethod` 均 `NoSuchMethodException`）⇒ 版本读取走**公开 API 双取法**（系统上下文 `PackageManager.getPackageArchiveInfo` → 宿主 Application `getPackageInfo`）并**延后探测**（`MountScheduler.postDelayed` 重试表 0/200/600 ms）。
  **ART 对「成员不存在」与「被 hidden-API 黑名单拒绝」抛同一种异常类型** ⇒ 反射探针拿到异常**不能**直接判成黑名单拦截；下「被拦」的结论前必须另找证据（成员清单 / AOSP 源码 / 不依赖该成员的公开路径能取到值）。另：`ApplicationInfo` 无 `versionName` 字段 ⇒ libxposed 的 `getApplicationInfo()` 取不到宿主版本。
- **版本依赖型 target 一律用 `HostVersion.resolveHostVersion`**：`HostVersion.resolve()`（旧取法）在本 ROM 恒 null ⇒ 任何「按宿主版本选表 / 选坐标」的逻辑接它 = 永远走基线（xhs 的 9.49.1 覆盖套就因此**从未生效**，2026-10-20 修复）。覆盖表还要区分「显式 null = 该版本无此点」与「无覆盖项 → 回落基线」两种 null，否则覆盖套里的空点会错误回落基线坐标（`XhsPoints.cls()` 三态 + `XhsPointsTest` 钉住）。
- **失败分级**：`FAILED` = 挂载抛异常，重试无意义；`NOT_RESOLVED` = 类/依赖未就绪，随类加载重试。
- **挂载类型要分**：改返回值 / 条件短路（只对目标参数生效，避免误伤无关判定，如 `hasPrivilege(14)` 只短路特权位 14）/ 前置改写（PRE_PROCESS，proceed 前修状态、失败不动）/ 键值覆盖（KEY_OVERRIDE，表驱动云控）。
- **幂等与防重装**：挂在注册表层保证；实现内不加 installed 标志；多包共享进程需对象级去重。

## 五、防御与可观测（底线，不是加分项）

- **异常隔离**：hook 回调里任何异常都必须吞掉并记日志——绝不能炸宿主进程。
- **per-key 降级**：每个子功能可独立关，而不是逼用户卸载模块。
- **日志是黑盒里唯一的眼睛**：判据统一 `installed N/M` 汇总；触发类日志节流，别刷屏。注意**宿主 logger 的 INFO 常不落 logcat**（只有 WARN/ERROR）⇒ 载荷类证据要靠模块侧探针打。

## 六、验证铁律（本项目血泪）

1. **判据先对版本**：真机 UI 与结论不符时，第一步 `dumpsys package` 对宿主版本 vs 逆向基线；`installed N/M` 里 N 明显小于 M = 版本错位或选点失效，**别先改 hook 实现**。
2. **目标方法存在性以设备实机 APK 的 dex 为准**：`adb shell pm path` 拉包 → dex 字符串检索。jadx 产物只作阅读参考（曾出现 jadx 有 `getIsVipUser`、设备包只有 `isVipUser` ⇒ 真机挂载失败）。
3. **删点必须真机 A/B**：静态推理"这段冗余"被真机回归打脸过一次（漏斗/旁路/null 实例都出自静态推理的盲区）。
4. **重装即被停用**：覆盖安装后 LSPosed 停用模块（表现为进程活着但零模块日志）⇒ 重新启用；按需拉起的进程还需 force-stop 一次。
5. **破坏性效果不由 AI 实测**：AI 交付 = 代码 + 构建通过 + 用户自执行的验证清单。
